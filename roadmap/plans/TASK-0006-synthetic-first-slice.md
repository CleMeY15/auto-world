# TASK-0006 delivery plan — honest synthetic search slice

Status: proposed for TASK-0006 review; a plan, not a running product or image admission.
Owner: Product/architecture. Decision sources: [ADR-0012](../../docs/decisions/ADR-0012-synthetic-development-lane.md), [DESIGN.md](../../DESIGN.md), [UX contract](../../docs/PRODUCT_UX.md), [vehicle schema](../../docs/decisions/ADR-0001-canonical-vehicle-contract.md), [Source Registry](../../docs/decisions/ADR-0002-source-registry-contract.md), [Connector SDK](../../docs/decisions/ADR-0003-connector-sdk-contract.md) and [API appendix](../../docs/decisions/ADR-0003-connector-sdk-api.md).

## Outcome and honest limitation

Deliver one responsive, accessible Search → Results → Synthetic listing detail → Saved flow on deterministic offline fixtures. A user can filter, inspect observed price/mileage and their internally traceable raw provenance, save/remove/reopen a listing locally, and understand contradictions or withdrawal. The persistent label is “Démonstration — données entièrement synthétiques, aucun véhicule à vendre.” There is no external source, seller CTA, real photograph, production credential, image/container, VIN disclosure, valuation, Deal/Trust Score, imported tax claim or account.

The accepted V1 `Observation` fields are only price, mileage, power, CO2 and internal-only VIN. The accepted SDK currently produces unresolved `Listing` records with listing-scoped observations; it does **not** create a `VehicleEntity` or resolve vehicle identity. V1 has no make/model/year/location/media or listing lifecycle on the public record. Therefore the first card says “Annonce de démonstration” plus a stable neutral number and displays only observed price/mileage (and a local illustration explicitly labeled as such). Missing fields say “Non renseigné”; no component derives automotive specifications from a raw string. Adding richer fields or a resolved vehicle page later requires a versioned schema/ADR, identity resolver and provenance tests before API/UI coupling. The P1 target is a thin interaction/evidence proof, not a misleading marketplace preview.

## Two paths, one canonical boundary

| Path | Sequence | Claim allowed |
| --- | --- | --- |
| Offline synthetic | Versioned local fixture bytes → existing `runConnector`/authenticated test-only authority → immutable raw SHA-256 and pending checkpoint → strict decoder → existing mapper/listing-version/observation/tombstone logic → injected in-memory store → read/search port → versioned demo API → responsive web | Deterministic contract, accessible flow and fixture-limited latency only. The store under `connectors/_sdk/test` is evidence for SDK behavior, **not** a deployable store; implementation may reuse its test vectors but must place demo-only composition behind an isolated entrypoint. |
| Supported target | Authorized source and authentic registry/evidence → same SDK/public vehicle contracts → admitted-image PostgreSQL durable transactions/outbox and raw retention → OpenSearch projection (Redis/S3-compatible roles only as justified by the accepted stack) → API → web | No claim until TASK-0005A/TASK-0005 acceptance, migration/replay, index reconciliation, restart, backup/restore, failure isolation and source-rights activation pass on exact subjects. |

The synthetic adapter has no network transport or Docker import. The demo API may use a local loopback connection for UI testing, but tests assert zero external network egress. Production build/import and deployment entrypoints must reject the test-only authority/fixture modules. Test fixture `legalStatus: dealer_feed` is solely a structural SDK input, never evidence of a dealership agreement. The authority port is still invoked and checked; “authenticated” here means the test contract is satisfied inside the isolated composition, not that an operator, legal document or production registry has been authenticated.

## Contract, ownership and consistency

- `packages/vehicle-schema` owns immutable `VehicleEntity`, `Listing`, `Observation` and provenance. Do not expose its internal VIN shape as a public DTO. `packages/source-registry` owns declared rights vocabulary; `connectors/_sdk` owns acquisition, raw-first mapping, idempotent receipts, explicit tombstones and full reconciliation. No web/API code reimplements these rules.
- `connectors/synthetic` owns only the production-excluded fixture adapter and ingestion harness, never search/business logic. Use a fixed corpus version and SHA-256 over exact UTF-8 bytes; keep raw bytes separate from normalized evidence. TASK-0101 extracts/reuses the existing `connectors/_sdk/test/store.mjs` implementation as an explicit dev/test-support boundary, preserving SDK lifecycle tests and excluding that support path from production exports/builds. It freezes the read/query **contract**, not an implementation of that port. TASK-0102 owns `services/api/demo/createSyntheticDemoReadPort`, the sole production-excluded composition factory importing that connector/test-support store and implementing/testing the public `DemoReadPort`. Only the API demo entrypoint imports this factory; API core depends solely on `DemoReadPort`, with no `services/api` → `services/ingestion` source import, additional transport or duplicated transactional store. One valid, one malformed, one contradictory and one withdrawn publication are mandatory, plus empty/partial variants for UX states.
- The read/search port operates over committed **projections** and immutable observations from the SDK store. Stable publication identity is `(sourceId, sourceListingId)` with public `ListingId`, never URL; no `VehicleEntity` is created or associated and no cross-publication deduplication occurs in this slice. Observations internally retain `sourceId`, `observedAt`, acquisition method, confidence and raw `{snapshotId, connectorRunId, sha256}`. Latest display value is deterministic by observed timestamp then stable observation ID; the complete contradictory history remains accessible. A withdrawal removes a publication from active search but preserves the historical listing/evidence state.
- `packages/demo-search-contract` owns only the public `DemoSearchQueryV1`, `DemoResultV1`, `DemoSearchResponseV1` and `DemoReadPort` types/validators, with no store or router. TASK-0101 freezes their focused ADR before API and web couple to them. Query permits price maximum, mileage maximum, stable sort and opaque cursor only; unsupported natural-language input yields an editable, non-destructive validation state rather than invented filters. The result DTO carries a stable `ListingId`, explicitly observed price/mileage or `unavailable`, and sanitized public evidence (opaque evidence ID, observed time, confidence and value). The response envelope carries `schemaVersion:1`, `dataMode:"synthetic"`, fixture version, `dataAsOf`, `state:"complete"|"partial"|"stale"`, results, an opaque next cursor when present, and a bounded reason code for non-complete states. `dataAsOf` is the committed read-projection watermark, not wall-clock response time. `partial` means a known incomplete result set; `stale` means the freshness bound was exceeded. The UI labels both states, does not assert a complete count, preserves filters and offers retry. The ADR must freeze exact meanings, transition/compatibility rules and V2 behavior for breaking changes. Internal source/run/snapshot IDs, raw SHA-256 and bytes stay behind the read port for authorized operational trace; they never enter public DTOs. VIN, policy evidence, seller PII, unsupported model/year/photo fields and real-source URLs are excluded. API responses use typed errors, request IDs and cursor pagination; complete-state counts are fixture-scoped, never global inventory claims.
- API read projection is authoritative for returned results; an LLM is never in the path. The target OpenSearch index will be eventually consistent behind the same read-port contract and must reconcile against PostgreSQL. No synthetic success can prove that projection, persistence, migrations or recovery.
- Preserve existing SDK atomic mutation/outbox kinds and idempotency keys; a read model consumes committed effects only and never rewrites raw, observation or tombstone history. Production PostgreSQL migrations, backwards-compatible reader versions, replay, index backfill and rollback are specified and tested in the later supported-integration task, not simulated as “Done” by an in-memory map.

## User flow and state contract

1. Search opens with one prominent field and two honest filters (observed price and mileage). Advanced criteria stay collapsed. The demo disclosure is always visible. Unsupported query language remains in the field with a clear explanation; no AI-generated parsing claim.
2. Results announce a fixture-scoped count, retain active filters/reset/undo and show stable-height cards with a local labeled illustration, neutral listing title, observed price/mileage and favorite control. Each fact links to sanitized evidence. No “best deal”, source-count or seller-visit CTA.
3. Synthetic listing detail preserves search scroll on return. It shows observed facts first, then a progressively disclosed chronological evidence rail with timestamps, confidence wording and opaque public evidence IDs. Internal raw-reference details are available only to authorized operational tooling, never the public demo API. Contradictory values are both visible; withdrawn state says unavailable without deleting history.
4. Save/remove is optimistic and reversible. `Saved` is accountless and device-local under a versioned `localStorage` key; reload/reopen retains valid IDs, stale/withdrawn items are labeled, storage denial/quota/corruption is recoverable without false success, and empty Saved links back to Search. On API disconnection, Saved IDs remain viewable/removable with details marked unavailable; Search/Detail preserve context and offer retry rather than claiming offline search. No account sync or telemetry of raw query/VIN.

The UI task must verify skeleton, empty, slow, error, offline, partial and success states at 320, 390×844, 768×1024 and 1440×900 viewports, light/dark and reduced motion. No clipped content, horizontal overflow or layout shift. Keyboard-only and screen-reader flows cover search, filters, detail, evidence, save/remove and return focus. [WCAG 2.2 AA](https://www.w3.org/TR/WCAG22/), visible focus, text/controls contrast, non-color-only status and ≥44×44 CSS px touch targets are gates; 44 px is an intentional product target above the [AA 24 px minimum with exceptions](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum), not a misstatement of AA. Screenshot evidence and independent UX review are required; a technically working but crude UI fails. Use [DESIGN.md](../../DESIGN.md) as the UI decision contract, not invented component styling.

## Measurement, privacy and operations

- Search API fixture benchmark: p95 <500 ms outside generation, measured on a stated CI/local profile; not extrapolated to millions of real listings. Input response/interaction target ≤100 ms for local filter and favorite feedback. Web [Core Web Vitals](https://web.dev/articles/vitals) targets on representative throttled mobile: LCP p75 ≤2.5 s, INP p75 ≤200 ms, CLS p75 ≤0.1. Record environment, sample size and failures; avoid hard-coding a pass from a tiny corpus.
- Allowlisted synthetic analytics: `search_submitted`, `results_rendered`, `filter_changed`, `listing_opened`, `favorite_added`, `favorite_removed`, `history_opened`. Allowed dimensions are fixture version, result count and field name; never query text, raw bytes, VIN, source URL, policy/credential references or persistent user identifiers. No analytics transport is required for the local demo; tests can assert event shape and redaction.
- Fixture health signals: run success/failure, parse-error rate, data completeness by accepted field, age/staleness, invalid-price rate and withdrawal count. Emit bounded SDK codes and a test assertion that repeated failures trip the configured circuit and a dev-only alert, without claiming a deployed dashboard/pager. The accepted Source Registry health function is monitoring input, never authorization.
- API observability is an executable contract, not a dashboard promise: propagate a generated or validated request ID through `DemoReadPort`; emit allowlisted `api_requests_total` by route/status, `api_errors_total` by bounded code and `api_request_duration_ms` histogram, plus `api.search` and `read_port.query` trace boundaries to a test sink. Structured logs include request ID, route, status, duration and bounded error code only; tests reject raw query text, VIN, source identifiers, raw hashes, fixture payloads and persistent user identifiers in logs, metrics and traces. External telemetry transport is out of scope for the synthetic lane.
- Supported projection operational contract: the outbox consumer uses bounded retry/backoff (at most five attempts per event); exhausted/poison events are quarantined with immutable diagnostic evidence and do not advance the consumer checkpoint. An operator-reviewed replay resumes from the failed event; silent skip is forbidden. In the bounded fixture test profile, committed-to-queryable index lag is ≤60 seconds in healthy runs; lag >60 seconds for five continuous minutes triggers a warning, while quarantine/checkpoint halt triggers an immediate critical test alert. These are acceptance thresholds for the fixture profile, not production SLOs; TASK-0105 measures and records samples, lag and alert behavior.
- Supported recovery is likewise bounded evidence, not an unearned production SLA. TASK-0106 captures an isolated backup after the final known committed synthetic write and records that watermark and backup timestamp (≤5 minutes old when restore starts). The backup covers PostgreSQL raw bytes/metadata, checkpoints, immutable listing/observation history, ledger and outbox. Relative to that captured watermark, the bounded fixture profile targets RPO 0 and restore plus OpenSearch rebuild/query reconciliation within 10 minutes. Test the objective, record elapsed time and failures; establish production RPO/RTO separately before real-source exposure.
- Incident/takedown: immediately disable the demo composition/build entrypoint and show a clear unavailable state; preserve test evidence only within its fixture retention. A real-source revocation/takedown must stop ingestion/publication through the authenticated registry, apply lawful retention/deletion and alert an owner; this cannot be “tested away” with synthetic fixtures and blocks real activation.
- Synthetic rollback: revert the focused task/PR or disable the dev/test entrypoint; no server data migration. Versioned local favorites must be read safely after rollback, with export/clear recovery and no silent data loss. Supported rollout requires versioned backwards-compatible database migrations, replay/backfill, verified backup/restore and a stop/rollback runbook in its own task.

## Contract trace and stop conditions

Review the four corpus scenarios end-to-end: valid → observed price/mileage with exact raw hash; malformed → bounded error, no canonical publication; contradictory → two retained observations and deterministic display selection; withdrawn → absent from active results, historical evidence retained. Inject revoked test authority, expired raw, partial full run, stale read projection, API failure, offline UI, invalid local storage and rollback. Each must fail closed or offer an honest recovery path, never fabricate missing values.

Stop implementation if cross-service DTO semantics drift from the frozen ADR, test-only modules appear in a production import graph, external network/image executes in synthetic mode, a fixture is treated as legal authorization, observed evidence is overwritten, a real VIN/source/seller claim appears in UI, or an applicable quality gate is red. Local loopback API testing is the only network exception in the demo composition. TASK-0006 itself is Done only after the plan/task contracts pass independent architecture, data-rights, security, UX/accessibility and SRE review, docs CI, final-head CI and merged-main verification; that does not mark any implementation task Done.
