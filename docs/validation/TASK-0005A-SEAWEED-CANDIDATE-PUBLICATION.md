## Publication transaction

The new manual workflow accepts no input and runs only on reviewed protected `main`, on its first run and first attempt. It uses a GitHub-hosted Linux runner and only `contents: read`, `actions: read` and `packages: write`. It has no OIDC, attestation or signing capability. The fixed source-artifact policy authenticates the original source run and its artifacts; an expired, absent or changed artifact fails before registry write. The checked-out recipe and current protected-main commit must match the run identity.

The runner must have at least 12 GiB of temporary free space and Docker server 28.0.4. Node is pinned to 22.23.2 and official Actions to commit SHAs. The job is bounded to 180 minutes, with a 165-minute publishing step and a 150-minute internal operation budget; cleanup and receipt emission retain separate time within the outer limits.

The existing candidate materializer verifies the flattened filesystem, replacement Go executable, omitted Rust helpers, notice set, image configuration, single-layer saved archive and local image identity. During its archive-inspection callback the publisher copies the already-validated Docker archive to a separate private temporary file and verifies the copy's hash and size. Only after the materializer has removed its own image and archive may the publisher load that copy, check the resulting local image, apply a unique run-scoped tag and attempt one push to the existing private package.

Immediately before the push, the publisher must confirm that its fixed remote tag is absent, and that the package's fixed bootstrap digest remains anonymously denied and authorized to the workflow. A network, authentication or registry error is not proof of tag absence. Once a push is attempted, its outcome is `ATTEMPTED_OUTCOME_UNCONFIRMED` until authenticated remote manifest reads by tag and digest confirm one subject with the exact saved config identity and one allowed layer descriptor. The candidate's exact digest must also be denied to an isolated anonymous read. A confirmed object is `PUBLISHED_UNADMITTED` even if a later privacy control or local cleanup fails; the overall result then remains failed. Ambiguous attempts must not be retried or relabelled without remote inspection.

The saved archive contains an uncompressed layer; the registry manifest describes Docker's compressed layer. Its descriptor is recorded separately and is not asserted equal to the saved layer hash or DiffID. This publication binds the config digest and remote manifest, while actual remote layer retrieval and decompressed-byte verification remain pending in a separate read-only run on a fresh runner. The publication receipt cannot substitute for that proof.

The chosen managed path is supported by the pinned [Docker 28.0.4 loader](https://github.com/moby/moby/blob/v28.0.4/image/tarexport/load.go#L89-L144), which creates the image from the saved config bytes, and its [push implementation](https://github.com/moby/moby/blob/v28.0.4/distribution/push_v2.go#L450-L514), which can compress an uncompressed layer. [Buildx's raw printer](https://github.com/docker/buildx/blob/v0.37.1/util/imagetools/printers.go#L35-L68) emits the registry manifest bytes. Its pinned [Containerd resolver](https://github.com/containerd/containerd/blob/v2.3.4/core/remotes/docker/resolver.go#L295-L368) maps an authenticated 404 to the reference's `not found` error; authorization and transport failures remain distinct and cannot authorize a write as an absent-tag result.

The public Actions artifact contains only a bounded technical receipt: recipe and source identities, archived image/config/layer/DiffID identities, target tag and manifest digest, phase durations, result and owned-cleanup state. No source ZIP, saved Docker archive, private image layer, Docker configuration, token, raw registry response or unfiltered command output is uploaded. All local images, tags, temporary archives and credentials must be removed with identity and final-absence checks. The workflow never starts or creates a container from the candidate.

## Evidence required before dispatch

The exact workflow, code, fixed package/credential/retention plan and tests require sequential approval by an Architect and then a distinct Critic before the first candidate write. Targeted hostile tests, full repository checks, independent implementation review, exact-head CI and merged-main CI must pass. The authenticated Settings observation and private-read receipt are prerequisites, but neither admits a candidate. Dispatch is withheld until these checks are recorded.

After a successful write, a separate read-only job must audit and exercise the exact published manifest digest using fresh scanner databases, then verify the private retained closure, official attestation and supported consumer admission. The earlier disposable local audit, this publication receipt and the bootstrap access proof are different subjects and authorities. TASK-0005A and TASK-0005 remain `IN_PROGRESS`; TASK-0006 remains blocked.

The candidate and its unique tag are retained in the existing private package without automatic deletion. This is staging retention, not a supported-runtime archive or proof of a second copy. Before activation, the complete image/source/compiler/module/notices/recipe/SBOM/reports/attestation closure must be retained for the declared supported life plus 365 days, copied to existing ignored private local storage and actually restored. Finite Actions artifacts and this public receipt do not satisfy that requirement. No new storage service or expanded local token is assumed. The vulnerability database must remain under 48 hours old at each applicable audit; the Java database age is recorded without a maximum-age rejection under the user's decision.

Rollback disables the publisher through a reviewed change and preserves any confirmed or uncertain remote object and receipt for investigation. It does not delete registry evidence, source artifacts, local service data or backups.
