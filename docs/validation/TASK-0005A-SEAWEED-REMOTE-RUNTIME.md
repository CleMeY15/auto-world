## Exact stored-data readiness plan

The focused increment validates the exact persisted chunk identity after the source write, then proves the restored volume's master registration and direct serving of the expected bytes before the existing single signed S3 read. Both restart persistence and backup restoration use this predicate. Internal metadata is bounded and parsed structurally, with fixed loopback endpoints and no publication of chunk identifiers, response bodies or credentials. Existing total time budgets, body integrity, ownership and cleanup controls remain mandatory. This repairs the demonstrably incomplete readiness contract without inventing a diagnosis for historical generic failures. Independent review, full verification and the actual third-run success are recorded above.

Closed public error groups distinguish invalid metadata, changed identity, invalid registration, direct-byte mismatch, readiness deadline and invalid probes. Source capture and restored read checks use the same groups; unknown failures retain bounded generic reasons. The remote receipt applies both sanitizers before publication. Tests exercise real POSIX probe scripts with a controlled curl adapter, parser edge cases, deadline exhaustion, transient responses, lifecycle ordering and cleanup. Native Linux CI must execute the POSIX cases that Windows cannot run.

Architecture review selected one small shared readiness transaction with pure Node parsers and the existing injected Docker adapters. Each caller retains its own lifecycle and cleanup. The original chunk descriptor is captured before source shutdown and must match after restart/restore. Both isolated persistence and backup commands explicitly advertise `-ip=127.0.0.1`, so master registration can require that same fixed endpoint; omitted `-ip` previously used automatic host-address detection. Basic/strict runtime and host-loopback profiles remain outside this change. Master lookup plus a direct exact-byte read provide the required predicates without adding `/status` or `/healthz` protocols. One absolute 390-second deadline covers generic readiness, stored-data checks and the final signed read, including a 12-second reserve for its 10-second request. Only transient readiness observations may be polled; invalid or changed identities, unexpected authorization/status and corrupt bytes fail immediately. The shared protocol and updated persistence/backup command fingerprints must reject old proof claims.

The parser contract comes from the pinned source, not an assumed REST schema: the [filer metadata handler](https://github.com/seaweedfs/seaweedfs/blob/c5073360007d28385a33426a42ac3e4ec504c5a3/weed/server/filer_server_handlers_read.go#L122-L134) serializes [filer.Entry](https://github.com/seaweedfs/seaweedfs/blob/c5073360007d28385a33426a42ac3e4ec504c5a3/weed/filer/entry.go#L13-L50) with `FileSize`, `Content` and `chunks`; each chunk carries both `file_id` and structured `fid`. The [file ID formatter](https://github.com/seaweedfs/seaweedfs/blob/c5073360007d28385a33426a42ac3e4ec504c5a3/weed/storage/needle/file_id.go#L21-L71) uses canonical lowercase byte-aligned key hex and an eight-digit cookie. The uint64 file key must be parsed losslessly and checked against the textual form. The pinned Node 22.23.2 runtime was directly verified to expose the original numeric token through the JSON reviver's `context.source`. [Volume defaults](https://github.com/seaweedfs/seaweedfs/blob/c5073360007d28385a33426a42ac3e4ec504c5a3/weed/command/volume.go#L381-L441) and [master lookup](https://github.com/seaweedfs/seaweedfs/blob/c5073360007d28385a33426a42ac3e4ec504c5a3/weed/server/master_server_handlers.go#L35-L140) justify exact local registration only after the explicit IP pin.
