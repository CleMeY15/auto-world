## Operational and completion boundaries

The SDK has durable versioned mutation/outbox records plus sanitized best-effort events. A real store must authenticate current rights, enforce fences and atomic CAS/receipt semantics, quiesce old in-flight writes on recovery, and execute all retention/cache/PII/media/takedown obligations. The test store is an in-memory atomic fault model, not production durability or authority proof.

Real-source rights approval, source-specific representative fixtures, source-health dashboard and tested alerts remain mandatory before first real source activation. They are not implemented or waived by this generic SDK task. UI/visual/a11y/customer analytics gates do not apply to this internal SDK; no customer-facing surface exists. Resource budgets and cancellation are contract-tested, not a production throughput benchmark or synchronous CPU preemption guarantee.

V1 is additive and internal; no database migration or deployment occurs. Rollback: disable source/callers, revert compatible SDK code, preserve receipts/checkpoints/raw/evidence subject to lawful retention, and establish compatible state before re-enabling. Never erase history or reinterpret a persisted key to retry.
