## Remaining acceptance

The eighth main-branch dispatch executed the strict conditional-write probe on a newly built disposable image. Two signed HTTP/1.1 `If-None-Match: *` PUTs targeted a proven-absent key through separate in-container loopback connections. The client withheld both fixed bodies until complete `100 Continue` responses arrived from both connections, then required exactly one HTTP 200 and one HTTP 412 and a signed SHA-256 GET matching the identified winner. A missing interim response, early final response, unexpected status, timeout or readback mismatch would have failed without a V4 receipt. The requests used normal hex payload hashes and SigV4 service scope `s3`: the pinned [SeaweedFS authentication path](https://github.com/seaweedfs/seaweedfs/blob/c5073360007d28385a33426a42ac3e4ec504c5a3/weed/s3api/auth_signature_v4.go#L560-L567) does not read the body before the [initial conditional check](https://github.com/seaweedfs/seaweedfs/blob/c5073360007d28385a33426a42ac3e4ec504c5a3/weed/s3api/s3api_object_handlers_put.go#L99-L130), and [Go 1.26.8 emits `100 Continue` on first body read](https://github.com/golang/go/blob/go1.26.8/src/net/http/server.go#L939-L953). The double interim response establishes that both handlers passed the initial check before either body was released; it does not identify the later Seaweed internal write path or prove arbitrary multi-host concurrency. The diagnostic retained no published port, read-only Actions permissions and owned-resource disposal. Rollback removes the V4 path and restores the reviewed V3 workflow definition; it cannot erase the historical run-8 result.

This diagnostic cannot prove host-loopback publication while Docker networking is disabled. Run 4 proves signed create, conditional PUT and GET with exact SHA-256 readback in `aw-raw`; exact HTTP 403 for a wrong key and a forbidden bucket; exact HTTP 412 for sequential replay and overwrite; and one background PUT pair with one winner and matching readback. That single pair did not establish request overlap; run 8 separately established one double-barrier contention pair with exact 200/412 and signed winner readback. Runs 5 and 6 produced no persistence evidence and each cleaned its owned resources. Run 7 verified the narrower same-runner case: a signed object survived removal of the first service container and was read by a distinct second container using the same local volume. Backup and restore, host-loopback publication, a fresh complete SBOM/vulnerability audit and private admission remain open. The [latest official Java DB build run](https://github.com/aquasecurity/trivy-java-db/actions/runs/35408377819) finished on 19 September 2026, more than 48 hours before this 24 September checkpoint; no newer run appears in the [upstream workflow history](https://github.com/aquasecurity/trivy-java-db/actions/workflows/cron.yml). The scanner freshness gate remains blocked until actual database bytes and `UpdatedAt` are checked in a fresh audit. The external fork access test is `SKIPPED_BY_USER` and its boundary remains `NOT_VERIFIED`.
