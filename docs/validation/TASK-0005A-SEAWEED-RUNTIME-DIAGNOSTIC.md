The runtime starts only on a fresh GitHub-hosted Ubuntu runner under Docker 28.0.4, on protected main, the individually reviewed workflow run and first attempt. Repository and Actions permissions are read-only. No port is published, no image or evidence archive is uploaded, and no registry write occurs. The synthetic S3 configuration is restricted to this disposable diagnostic and must be mode `0600`.

A short-lived initializer must first prove the volume empty, then set mode `0700` and ownership `1000:1000`; it runs as root with only `CAP_CHOWN`, while both service containers remain UID/GID `1000:1000` with all capabilities dropped. The first service container performs the signed conditional PUT and exact SHA-256 GET, then stops and is removed. A separately created second service container, using the same image ID and volume, must reach readiness and retrieve the same object with a signed GET and matching SHA-256. Run 5 stopped before the initializer started because its exact container-profile inspection did not account for Docker's canonical `CAP_CHOWN` rendering. Run 6 passed the owned-identity and mount check, then stopped at the remaining profile check. Run 7 accepted Docker's pinned `no-new-privileges=true` inspection value and required effective `NoNewPrivs: 1` at initializer entry and before each signed service probe. The proof is not a backup or restore test: both services reused one host-local volume on one runner.

The fixed command is ADR-0008's Go server/S3 profile. The diagnostic checks the derivative version, PID-1 identity, private `/tmp` mode, internal master readiness on 9333, filer readiness on `8888/readyz`, S3 readiness on `8333/readyz`, an exact HTTP 403 for unsigned `GET /` on 8333, absence of Iceberg/Lance listeners on 8181/9101, absence and failed direct invocation of both unsupported Rust helpers, and bounded shutdown. The V2 extension also checks signed create, conditional PUT and GET with exact readback, wrong-key and forbidden-bucket refusals, sequential conditional replay and overwrite refusals, and one background conditional PUT pair with matching winner readback. The container, runtime configuration, image, saved archive, rootfs and temporary directories must be cleaned before a success receipt. A random per-run label and image-ID inspection recover ownership even if Docker creates a container but loses its command response; a foreign or uncertain container is preserved and blocks success. Public diagnostic output contains only fixed phase/result/reason, bounded duration, run/revision identifiers and an image hash when known; it never includes raw Docker output or the synthetic credential. A failure or uncertain cleanup does not authorize a retry that bypasses a control.
