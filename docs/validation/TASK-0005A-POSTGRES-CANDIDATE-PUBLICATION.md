## Capability boundary

Use a new input-free manual workflow on reviewed protected `main`, guarded to its first run and first attempt. The publication job has only `contents: read` and `packages: write`; no OIDC, signing or attestation permission. [GitHub grants permissions to the whole job](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#how-permissions-are-calculated-for-a-workflow-job), so omitting `GITHUB_TOKEN` from early child environments does not create a step-level privilege boundary. The audited publisher process receives the Actions token, excludes it from every build/export child environment and context, and uses it only for `docker login` through stdin after local proof. This stage does **not** run the PostgreSQL diagnostic, the candidate, the scanner or any candidate helper. It may run the reviewed Dockerfile's bounded offline `RUN` to construct the image: pre-pull the exact public base by digest, use `docker build --network=none --pull=false`, fixed cgroup limits, pinned material bytes and no secret, SSH, token, Docker-auth directory or host socket passed to the build context.

No private image archive, layer, Docker configuration or scan report may cross jobs or be uploaded as an artifact in this public repository: [artifacts on public repositories can be read through GitHub's API](https://docs.github.com/en/rest/actions/artifacts#list-workflow-run-artifacts). The only public artifact is one bounded, redacted technical receipt. The private GHCR object is staging storage, not the required supported-lifetime second copy. That copy and a real restore remain admission gates.
