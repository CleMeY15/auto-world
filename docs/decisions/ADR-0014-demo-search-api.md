## Decision and implementation plan

Real HTTP lifecycle follow-up: the application-owned five-second deadline and read signal must remain independent of framework incoming-message completion. Node22 normal incoming `close` is not by itself client disconnect; only an aborted incoming request or unfinished outgoing response closure cancels as disconnect. Actual socket success/detail/error/deadline regressions are required in addition to injection. The focused implementation/evidence is recorded in [the follow-up](../validation/TASK-0102-real-http-lifecycle.md); the public V1 protocol and isolation scope remain unchanged.

The application deadline is exactly5000ms and uses its own AbortController rather than Fastify5.12.5's handlerTimeout/request.signal. Socket inactivity connectionTimeout is5500ms solely to leave a bounded500ms window for the writable closed408 after the application deadline; body requestTimeout, headersTimeout and keepAliveTimeout remain5000ms. This is not a longer read-port deadline. [Node22 incoming-message close semantics](https://nodejs.org/download/release/v22.23.2/docs/api/http.html#event-close) and [Fastify async reply completion](https://fastify.dev/docs/v5.0.x/Reference/Routes/#async-await) explain the correction; no framework upgrade or fork is required.

Use the roadmap-selected Fastify/TypeScript stack with exact fastify5.12.5 (stable v5, Node20+/22 supported) and dev-only @types/node22.20.2 already used by web. [Exact security release](https://github.com/fastify/fastify/releases/tag/v5.12.5), [LTS](https://fastify.dev/docs/latest/Reference/LTS/), [TypeScript requirements](https://fastify.dev/docs/latest/Reference/TypeScript/) and [MIT license](https://raw.githubusercontent.com/fastify/fastify/v5.12.5/LICENSE) establish this selection. The new production dependency closure license inventory reports only MIT/ISC/BSD-3-Clause; installed-lock pnpm audit reports zero known vulnerabilities. Preserve third-party notices; no extra HTTP plugin/framework is introduced. API core in services/api/src consumes only the public DemoReadPort declaration and frozen public parsers. The separate services/api/demo factory composes connectors/synthetic's demo-condition harness over the existing SDK test-support store; it is excluded from the production build/export graph and refuses NODE_ENV=production. No ingestion service import, replacement store, database, external asset/network, generic router or AI parser.

HTTP routes are POST /v1/demo/search with the exact DemoSearchQueryV1 JSON body, and GET /v1/demo/listings/:listingId with no query parameters. Successful responses wrap the unchanged DemoSearchResponseV1 as {schemaVersion:1,requestId,data}. A known missing detail maps to bounded not_found; unsupported/invalid queries are editable invalid_query, never inferred. Typed failures use {schemaVersion:1,requestId,error:{code}} with a closed vocabulary and no caller values, stack, source text or exception messages. Read outcome failures map to invalid_cursor, read_unavailable or cancelled. Protocol failures use bounded invalid_request, method_not_allowed, unsupported_content_type and request_too_large codes.

HTTP status mapping is closed: 200 success; 400 invalid_query/invalid_cursor/invalid_request; 404 not_found (including unknown route); 405 method_not_allowed (including HEAD/OPTIONS on known routes); 413 request_too_large; 415 unsupported_content_type; 503 read_unavailable; 408 cancelled only while the socket remains writable. After client disconnect, record cancelled with internal status499 and never attempt a response. Known-route wrong methods deny; unknown paths are not_found without echo. Every writable response uses application/json; charset=utf-8, Cache-Control:no-store and X-Content-Type-Options:nosniff. No redirects, cookies, wildcard CORS or default Fastify error payload.

Request IDs are req_ plus32 lowercase hexadecimal characters. A valid single x-request-id is propagated; rawHeaders detects duplicates case-insensitively. Invalid/duplicate IDs reject with invalid_request and a newly generated server correlation ID, never echoing the rejected value. Generated IDs are random opaque correlations. The same ID and abort signal reach the read port and error response. Only fixed known routes enter logs/labels; unknown paths are never recorded as text.

The demo process binds 127.0.0.1 only. The bound port is an integer1..65535; demo entrypoint uses3210. Host must equal 127.0.0.1:<boundPort> exactly (no localhost alias, suffix, whitespace or duplicate). Reject every Forwarded and X-Forwarded-* header, even with an otherwise valid Host; no forwarded-header substitution is permitted. Origin may be absent or exactly http://127.0.0.1:<boundPort>; every other/multiple/null Origin rejects. Allowed Origin gets only exact ACAO and Vary:Origin; OPTIONS remains405, so TASK-0103 must use a same-origin web proxy rather than a cross-origin browser request. There is no arbitrary origin/host allowlist input; trustProxy is false and CORS denies by default. JSON search input is bounded to8KiB and unknown query strings/methods/content types reject. Local loopback tests are the only network exception. No credentials or external URL configuration exists. Read-returned DTOs are revalidated and detached before publication; every inspection, including hostile getters/proxies, stays inside the internal failure boundary. Malformed outcomes and thrown internal messages become read_unavailable. The application handler has a five-second deadline independent of socket/body timeouts and read-port cooperation; abort reaches the read port, the API stops awaiting abandoned work, and late outcomes cannot write or alter terminal telemetry. Deadline cancellation returns the closed 408/cancelled response while writable; only a real disconnected client records internal499. JSON whitespace is limited to SP, TAB, LF and CR. Record terminal read_port.query spans after DTO and route-specific validation so a rejected read never reports status200.

The demo read adapter reads exactly ADR-0013's manifest scope from SDK committed projections and immutable observations. It selects latest price/mileage by observed UTC time then ordinal observation ID; contradictory/withdrawn history is retained. Search includes active only, detail may show ended evidence. It never constructs VehicleEntity or exposes VIN/raw/source/run/snapshot/policy identities. Each call obtains exactly one atomic SDK snapshot. The demo factory reuses the SDK public parseConnectorCheckpoint export to validate, detach and freeze every manifest-scope stored run and embedded page checkpoint before association checks; malformed statuses, unknown keys, terminal fields on running checkpoints and hostile accessors fail read_unavailable. This is an additive export of the existing SDK validator, with no duplicate checkpoint schema or SDK production dependency in the API core. Inventory, projections, owning runs and page.committed/full.finalized ledger associations must match the exact manifest scope/source/territory/method. Every completed stored run derives its terminal receipt independently through completionOperationKey and the exact kind for full/incremental mode. Incremental page complete is boolean and equivalent to completed checkpoint status; full pages retain running checkpoints until full.finalized. Historical terminal receipts and their run/checkpoint ownership remain validated even after a later run completes. Matching recognized receipts must have exact nondecreasing UTC recordedAt timestamps; select their maximum recordedAt, with immutable ledger insertion order breaking timestamp ties. Regression/mismatch returns read_unavailable. The selected receipt supplies dataAsOf=record.recordedAt. complete always requires an authentic successfully finalized full baseline for this scope, plus the selected receipt being the owning completed run's completionOperationKey and finalInventoryGenerationId/revision equal the same snapshot head. Full mode requires its full.finalized. A completed incremental final page.committed may remain complete only when run.baselineGenerationId and current head ancestry match that scope's authenticated full.finalized baseline (full receipt/run generation and revision association verified); otherwise it is partial/projection_incomplete, or read_unavailable for an invalid association. Incremental completion over generationId empty never implies complete. Any later incomplete committed head is partial/projection_incomplete. Missing/mismatched associations or future watermark return read_unavailable; empty complete requires an authentic empty finalized run in this synthetic model. Age>60000ms yields stale/projection_stale before any partial rule; exactly60000 remains fresh. No clock/value fallback. Capture the manifest-scope generation/revision, recognized receipt and selected projection/history fingerprint as the cursor snapshot identity; unrelated runtime/raw bookkeeping does not create a projection watermark.

Cursors are opaque cur_ plus64 lowercase hex. Bind fixture version, exact committed projection fingerprint/watermark, normalized filters/sort (cursor excluded) and position in a per-adapter continuation map capped at1024 entries. Tokens are entropy-backed opaque hashes with a domain and snapshot epoch/binding; no internal ID is reversibly encoded. Retry random collisions at most four times, then read_unavailable. Memoize by binding+position; cursor replay is non-consuming and returns the same continuation token. No time-based eviction/TTL: validity lasts for the same committed snapshot and adapter lifetime, including stale reads. Clear current entries on committed snapshot replacement, advancing the epoch so old tokens cannot be reused. At capacity, existing continuations remain valid and allocation of a new one returns read_unavailable rather than evicting valid tokens. Changed query, replaced projection, unknown cursor and invalid page position reject. Fixed20-item pages; exact nextCursor iff another matching result remains; complete totalCount is global fixture-scoped count. Limits above10000matches/256evidence entries reject, with no silent truncation. Tests prove first/middle/last pages over SDK-committed synthetic test data, not only declaration validation.

Telemetry uses a bounded injected sink: api_requests_total{route,status}, api_errors_total{code}, api_request_duration_ms, structured request-ID/route/status/duration/code logs and api.search/read_port.query spans. Only the correlation ID and allowlisted event/count/field names appear; no request body/filter/cursor/VIN/source/raw/persistent-user data. Test-only bounded failure alerts are explicit; no deployed collector or pager claim.
